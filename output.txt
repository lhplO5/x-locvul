Bài báo được định vị thành evidence-grounded cascade:
Detection → source-grounded localization → evidence-grounded explanation.
Điểm mới có thể bảo vệ tốt hơn là: Multi-task vulnerability+CWE detection; source-constrained projection với phép đo hallucination trực tiếp; CWE-aware grounding cho explainer; và quan trọng nhất là đánh giá error propagation từ Stage 1 → Stage 2 → Stage 3. Cách định vị này khác với các hướng gần đây dùng LLM trực tiếp hoặc RAG/reasoning, đồng thời phù hợp hơn với AI for Software Engineering và trustworthy software analysis. UniXCoder thực sự được pretrain với cross-modal signals, bao gồm AST representation, nên có cơ sở để dùng làm encoder nhưng không nên diễn đạt quá mức rằng nó tự động “theo dõi data flow/control flow”. 
Tập trung vào 4 thực nghiệm bắt buộc + 2 thực nghiệm tăng sức mạnh, theo thứ tự:
E1 – Fair Stage-1 baseline, bắt buộc. Chạy trên cùng một split: CodeBERT single-task, UniXCoder single-task, UniXCoder multi-task. Báo cáo Vulnerable-F1, Precision, Recall, MCC, AUPRC, Balanced Accuracy, FPR; tối thiểu 3 seeds, mean ± std và 95% CI. Đây là thực nghiệm quan trọng nhất vì nó xác nhận liệu UniXCoder + CWE auxiliary task có thực sự tạo đóng góp. 
Kiểm tra lại split của kết quả thực nghiệm. Về chủ quan, thầy nghĩ phải tốt hơn.
E2 – Ablation của Multi-task Learning. Chạy λ_CWE = 0, 0.1, 0.25, 0.5, 1.0. Báo cáo cả Vulnerability-F1 và CWE macro-F1. Báo cáo gốc chỉ cho công thức nhưng chưa nêu cụ thể hai trọng số. Thực nghiệm này vừa khắc phục thiếu sót reproducibility, vừa chứng minh contribution của auxiliary CWE supervision. 
E3 – Hallucination/Localization ablation, rất quan trọng. So sánh raw CodeT5 generation → normalized exact matching → edit-distance/BM25 → SentenceTransformer cosine source projection. Ngoài Top-1/5/10, MRR và IFA, bổ sung hai metric mới: Generated-Line Hallucination Rate (GLHR) và Projection Rescue Rate (PRR). Không nên tiếp tục dùng ROUGE cao làm bằng chứng rằng “không hallucination”; ROUGE chỉ đo overlap chuỗi. 
E4 – Đánh giá Stage 3 định lượng. Lấy khoảng 100–200 vulnerable functions, ít nhất 10 CWE families. So sánh function-only Qwen vs function + localized line vs function + line + CWE vs oracle line + CWE. Đánh giá root-cause correctness, CWE consistency, evidence support, unsupported-claim rate và repair usefulness. Nên có ≥50 mẫu do 2 người đánh giá độc lập và báo Cohen's κ. Điều này đặc biệt cần thiết vì các nghiên cứu gần đây như Vul-RAG, R2Vul và VulInstruct đã đi khá sâu vào vulnerability reasoning/explanation; vì vậy X-LocVul không nên claim là “first explainable vulnerability detector”. 
E5 – Leakage-controlled/chronological evaluation. Giữ split 70/15/15 hiện tại để reproduction, nhưng bổ sung một protocol de-duplicated + chronological, theo tinh thần PrimeVul. Đây sẽ là điểm làm bài mạnh hơn đáng kể trước reviewer. Dataset hiện tại của báo cáo đang dùng merged PrimeVul/BigVul và chia 70/15/15. 
E6 – Runtime/deployment cost. Đo latency từng Stage, peak GPU memory, throughput và tỷ lệ hàm sạch bị Stage 1 loại bỏ trước khi gọi CodeT5/Qwen. Thực nghiệm này tương đối dễ nhưng rất hợp với track Software Engineering/DevSecOps của SoICT.

X-LocVul: Evidence-Grounded Cascaded Detection, Line Localization, and Root-Cause Explanation of C/C++ Vulnerabilities
Hoang-Phuong-Linh Le and Quyet-Thang Huynh
School of Information and Communication Technology, Hanoi University of Science and Technology, Hanoi, Vietnam
Abstract. Source-code vulnerability analysis is most useful to developers when it answers three questions together: whether a function is vulnerable, where the security-relevant statement is located, and why the statement is unsafe. This paper presents X-LocVul, a modular three-stage pipeline for C/C++ that combines a multi-task UniXCoder detector, a CodeT5 line generator followed by source-constrained semantic projection, and a lightweight Qwen2.5-Coder explainer. The prototype jointly predicts vulnerability and CWE labels at Stage 1, maps the generated localization back to an actual input line at Stage 2, and conditions natural-language explanation on the localized evidence at Stage 3. On the current held-out test split, Stage 1 reaches 95.71% accuracy and 64.57% vulnerable-class F1 with a 1.08% false-positive rate; Stage 2 achieves 66.62% Top-10 accuracy, 41.01% MRR@10, and median IFA of 4. A real CVE case also exposes a key limitation: the explainer can reason correctly about a missing bounds check while using an incorrect vulnerability term. We therefore formulate a leakage-controlled evaluation and a CWE-aware evidence-anchoring extension to quantify detection generalization, source-line hallucination, explanation consistency, and end-to-end error propagation. X-LocVul is positioned as an evidence-grounded software-security assistant rather than an unconstrained LLM classifier.
Keywords: software vulnerability detection, vulnerability localization, explainable AI, code language models, C/C++, DevSecOps.
Introduction
Vulnerability detection at function level is only the first step of a developer-facing security workflow. A binary warning still requires an engineer to inspect a potentially long function, identify the security-relevant statement, reconstruct the data-flow condition that makes it unsafe, and decide how to repair it. Recent code language models improve representation learning and generation, but realistic deployment remains difficult because benchmark leakage, class imbalance, line-level localization errors, and hallucinated explanations can make impressive aggregate scores misleading.
The X-LocVul project starts from the LocVul idea of coupling function-level filtering with sequence-to-sequence line localization [1], but extends the workflow in two directions. First, the detector is implemented as a UniXCoder-based multi-task model with a vulnerability head and an auxiliary CWE head. Second, after localization, a small code-specialized LLM is used to explain the root cause and suggest a repair. The intended interface is therefore not merely a label; it is an evidence chain from a function-level decision to a source-resident line and then to a developer-readable explanation.
This positioning requires more careful evaluation than the original project report. PrimeVul has shown that de-duplication and chronological splitting can dramatically reduce apparent vulnerability-detection performance compared with conventional benchmarks [2]. Meanwhile, recent work on explainable and reasoning-oriented vulnerability detection demonstrates that explanation generation itself is now an active research problem [8–12]. Consequently, the contribution of X-LocVul should not be framed as being the first system to explain vulnerabilities. Instead, we focus on the modularity and grounding interfaces between detection, localization, and explanation, and on measurements that reveal how errors propagate across these stages.
We organize the study around three research questions: RQ1 asks whether auxiliary CWE supervision improves vulnerability detection under identical and leakage-controlled evaluation; RQ2 asks whether source-constrained semantic projection reduces generative line hallucination while preserving localization quality; and RQ3 asks whether conditioning a lightweight explainer on localized line evidence and CWE evidence improves security correctness and terminology consistency. A fourth practical question measures latency and resource cost of the cascade.
The paper makes the following contributions: (1) an evidence-grounded three-stage architecture joining vulnerability/CWE prediction, source-constrained line localization, and lightweight explanation; (2) a multi-task detector and a CWE-aware explanation interface designed to reduce unconstrained LLM behavior; (3) a direct evaluation protocol for line hallucination and projection rescue, rather than inferring hallucination from text-overlap metrics; and (4) an end-to-end experimental design that separates component quality from error propagation and explicitly controls dataset leakage.
Background and Related Work
Function-Level Vulnerability Detection and Dataset Realism
Big-Vul is a widely used C/C++ vulnerability dataset derived from real vulnerability-fixing commits [6]. Pre-trained code models such as CodeBERT and UniXCoder provide stronger semantic representations than task-specific models trained from scratch. UniXCoder in particular uses cross-modal pre-training signals that include source code, comments, and a serialized form of abstract syntax trees [3]. However, representation strength does not remove benchmark bias. Ding et al. introduced PrimeVul with stronger labeling, de-duplication, and chronological splitting, and showed that performance on earlier datasets can substantially overestimate real-world generalization [2]. This observation is central to our revised experimental design.
Line-Level Localization
LineVul formulates fine-grained vulnerability prediction at the line level and established ranking-oriented metrics for developer inspection [5]. LocVul later proposed a sequence-to-sequence localization approach in which a generated vulnerable statement is matched back to a line in the original function [1]. X-LocVul retains this useful source-projection principle while explicitly measuring when generation leaves the source and when projection repairs the error. This distinction is important because a high ROUGE score can coexist with token-level changes that make a generated statement unusable as a source location.
Vulnerability Explanation with LLMs
LLM-based vulnerability analysis has rapidly moved from unconstrained prompting toward structured security knowledge and reasoning. LLMVulExp specializes LLMs for vulnerability detection and detailed explanations [8]. Vul-RAG retrieves vulnerability knowledge distilled from historical cases and uses it to guide detection and explanations [9]. R2Vul distills structured security reasoning into a compact model [10], while VulInstruct guides reasoning with security specifications extracted from historical vulnerabilities [11]. LLMxCPG combines code-property-graph-guided context with LLM reasoning to preserve vulnerability-relevant context [12]. These studies motivate a narrower claim for X-LocVul: its novelty lies in an explicit evidence cascade and the empirical study of grounding and error propagation, not in explanation generation per se.
X-LocVul Architecture
Given a C/C++ function , X-LocVul constructs an evidence path across three components. Stage 1 returns a vulnerability probability and a CWE distribution. When the vulnerability probability exceeds a threshold , Stage 2 generates a candidate vulnerable statement and projects it onto the nearest line that actually occurs in f. Stage 3 receives the original function plus the localized line; in the revised design it additionally receives the predicted CWE label and canonical CWE name as an explicit security anchor.

Stage 3: Evidence-Grounded Root-Cause Explanation
The prototype uses Qwen2.5-Coder-1.5B-Instruct, a compact code-specialized model [7]. The function and localized line are inserted into a constrained prompt asking for the root cause, data-flow reasoning, and a repair direction. We use the term root-cause explanation rather than causal explanation because the system does not perform formal causal inference.
The revised version adds a CWE consistency guard. The prompt includes the predicted CWE identifier and canonical name, and requests a structured response with four fields: vulnerability type, source evidence, root cause, and repair. A lightweight validator then flags a response when its stated vulnerability type contradicts the Stage-1 CWE anchor. This extension is directly motivated by the observed CVE-2017-13036 case, in which the model correctly reasoned about an out-of-bounds read and proposed a bounds check but referred to the behavior as a buffer overflow.
Experimental Design
Datasets and Existing Prototype Setup
The current Stage-1 prototype uses a merged Big-Vul/PrimeVul corpus and a 70/15/15 train/validation/test split. The resulting test set contains 26,738 functions: 24,816 clean and 1,922 vulnerable. Training was performed with PyTorch/HuggingFace on an NVIDIA Tesla T4. The reported Stage-1 configuration uses learning rate 2×10^-5, batch size 8, three epochs, weight decay 0.01, and maximum sequence length 512. Stage 2 uses CodeT5 with learning rate 5×10^-5, 10 epochs, beam size 4, and label padding ignored by the cross-entropy loss. Stage 3 uses Qwen2.5-Coder-1.5B-Instruct with temperature 0.7 and a 512-token output budget.
Because a random function-level split can leave near-duplicates or temporally related fixes across partitions, the current prototype results are treated as preliminary. The final SoICT experiment will preserve this split only as a reproduction setting and add a de-duplicated chronological protocol following the design principles of PrimeVul [2].
For the leakage-controlled protocol, samples will be grouped by vulnerability-fixing commit and project before partitioning. Exact duplicate functions and high-overlap vulnerable/patched pairs that cross partitions will be removed or assigned to the same group. Training will use only commits older than the validation and test windows, and the final test set will remain untouched during threshold selection. We will publish the split manifest, sample counts, CWE coverage, and a hash of each function so that every model is evaluated on exactly the same examples. This protocol is deliberately stricter than the current random split and the resulting scores are expected to be lower, but they will support stronger claims about generalization.
The Stage-1 comparison will also separate the effect of the encoder from the effect of multi-task learning. CodeBERT single-task, UniXCoder single-task, and UniXCoder multi-task will share preprocessing, maximum length, optimizer family, checkpoint rule, and threshold-selection procedure. In addition to vulnerable-class F1, we will report MCC and AUPRC because they remain informative under severe class imbalance. Calibration will be characterized with reliability curves and Brier score where probabilities are used for thresholding; this is especially relevant because Stage 1 decides which functions incur the computational cost of Stages 2 and 3.

Stage-3 Case Study and Failure Mode
The prototype was exercised end-to-end on tcpdump CVE-2017-13036, labeled CWE-125 (out-of-bounds read). Stage 1 predicted the function as vulnerable with the correct CWE. Stage 2 projected the generated evidence to the source line “if (ndo->ndo_vflag > 1) {”. The Stage-3 model correctly recognized a missing bounds check and suggested an additional length check, but it described a read beyond the end of a buffer as “buffer overflow.” This is a small terminology error with an important methodological consequence: a fluent explanation can be logically useful while still being inconsistent with the security taxonomy.
This case motivates the line+CWE anchoring condition in E4. It also suggests reporting explanation correctness in multiple dimensions rather than a single fluency score. In the final paper, qualitative examples should include both successful explanations and failure cases, with all generated claims traceable to the input code, the localized line, or the known vulnerability metadata.
Discussion
Why a Cascade Instead of a Single LLM?
A single large generative model can in principle predict a vulnerability, identify a line, and explain it in one response. X-LocVul deliberately separates these responsibilities. The detector can be calibrated and measured as a classifier; the localizer can be measured as a ranking problem; and the explainer can be audited against explicit source evidence. This modularity makes failures diagnosable and allows the system to reserve the generative model for the comparatively small fraction of functions that pass Stage 1. The approach also supports oracle experiments that distinguish “the explainer failed despite correct evidence” from “the explainer inherited an upstream localization error.”
Threats to Validity
Dataset leakage is the principal internal-validity threat. The existing random split must not be used to make claims of real-world generalization. The chronological and de-duplicated E5 protocol addresses this risk, but may also reduce the number of vulnerable test examples. A second threat is label quality: CWE labels can be coarse, missing, or inconsistent across CVE metadata. We will report the coverage of the CWE auxiliary task and exclude samples without a defensible mapping from CWE-specific metrics. A third threat is model stochasticity; all trainable comparisons will use repeated seeds, and generation parameters will be fixed for evaluation.
Construct validity is especially important for Stage 2 and Stage 3. ROUGE measures text overlap, not source-line correctness, so direct hallucination and ranking metrics are required. Likewise, explanation fluency is not security correctness. Human scoring criteria will therefore separate root-cause correctness, evidence support, taxonomy consistency, and repair usefulness. External validity is limited to C/C++ function-level analysis; interprocedural vulnerabilities, configuration flaws, and other languages remain future work.
Practical Implications
The current detector favors precision over recall: roughly four-fifths of its positive predictions are true vulnerabilities, but almost half of vulnerable functions are missed on the present split. For an IDE assistant this may be a reasonable starting operating point because low false-positive volume is important, but a security gate may prefer a lower threshold and higher recall. The final paper should therefore report precision-recall curves and threshold sensitivity instead of committing to a single operating point. Stage-wise latency will further determine whether explanation should run synchronously in an IDE or asynchronously in CI/DevSecOps.
Conclusion
X-LocVul combines multi-task function-level detection, source-constrained line localization, and lightweight root-cause explanation in a single evidence cascade. The existing prototype demonstrates low false-positive rate at Stage 1 and useful Top-10 localization at Stage 2, while the CVE case study illustrates both the value and the risk of LLM explanations. The key step toward a publishable SoICT study is not to add more architectural complexity, but to make the evidence stronger: identical-data baselines, leakage-controlled evaluation, direct hallucination measurements, quantitative explanation assessment, and end-to-end error-propagation analysis. The proposed CWE-aware grounding guard provides a compact method extension that directly addresses the observed terminology failure and can be evaluated through controlled ablation.

def standardize_cols(df, split_name):
    df = df.copy() # Tránh warning của Pandas
    rename_dict = {}
    
    # 1. Tìm cột Code (Ưu tiên func_code > func > code > func_before của BigVul)
    for col in ['func_code', 'func', 'code', 'func_before']:
        if col in df.columns:
            rename_dict[col] = 'func_code'
            break
            
    # 2. Tìm cột Label (Ưu tiên label > target > vulnerable > vul của BigVul)
    for col in ['label', 'target', 'vulnerable', 'vul']:
        if col in df.columns:
            rename_dict[col] = 'label'
            break
            
    # 3. Đồng bộ Metadata (Đổi tên cột của BigVul về chuẩn hệ thống)
    if 'CVE ID' in df.columns: rename_dict['CVE ID'] = 'cve'
    if 'CWE ID' in df.columns: rename_dict['CWE ID'] = 'cwe_label'
    
    # Đổi tên và thêm cờ split
    df = df.rename(columns=rename_dict)
    df['split'] = split_name
    
    # BigVul thường chứa 'func_after' (code sạch), ta xóa đi cho nhẹ RAM vì bài toán này chỉ nhận diện code đầu vào
    if 'func_after' in df.columns:
        df = df.drop(columns=['func_after'])
        
    return df

def remove_comments_and_whitespace(code):
    """Loại bỏ comment C/C++ và các khoảng trắng dư thừa"""
    # Ép kiểu an toàn để chống lỗi 'float' object
    code = str(code) if pd.notna(code) else ""
    # Xóa block comments /* ... */
    code = re.sub(r'/\*[\s\S]*?\*/', '', code)
    # Xóa inline comments // ...
    code = re.sub(r'//.*', '', code)
    # Xóa khoảng trắng dư thừa, đưa về 1 dòng
    code = re.sub(r'\s+', ' ', code).strip()
    return code

def compute_sha256(text):
    # Đảm bảo đầu vào luôn là chuỗi trước khi encode
    text = str(text) if pd.notna(text) else ""
    return hashlib.sha256(text.encode('utf-8')).hexdigest()

def apply_cwe_mask(df):
    """
    Assigns correct CWE ID for vulnerable samples.
    Assigns -100 for clean samples to ignore them in CrossEntropyLoss.
    """
    # Ensure cwe_label column exists
    if 'cwe_label' not in df.columns:
        df['cwe_label'] = 'CWE-Other'
    else:
        df['cwe_label'] = df['cwe_label'].fillna('CWE-Other')

        lambda x: cwe2id.get(x['cwe_label'], cwe2id.get('CWE-Other')) if x['label'] == 1 else -100, 
        axis=1
    )
    return df

# ==========================================
import torch
import torch.nn as nn
from transformers import AutoModel, PreTrainedModel, AutoConfig

print("6. Defining Custom Multi-task Architecture...")

class UniXCoderMultiTask(nn.Module):
    def __init__(self, model_name="microsoft/unixcoder-base", num_cwe_classes=15):
        super(UniXCoderMultiTask, self).__init__()
        # Load the base UniXCoder model
        self.encoder = AutoModel.from_pretrained(model_name)
        self.config = self.encoder.config
        
        hidden_size = self.config.hidden_size
        
        # Branch 1: Binary Classification (Vulnerable vs Clean)
        self.classifier_bin = nn.Sequential(
            nn.Linear(hidden_size, hidden_size),
            nn.Tanh(),
            nn.Dropout(0.1),
            nn.Linear(hidden_size, 1) # Output 1 logit for BCEWithLogitsLoss
        )
        
        # Branch 2: CWE Multi-class Classification
        self.classifier_cwe = nn.Sequential(
            nn.Linear(hidden_size, hidden_size),
            nn.Tanh(),
            nn.Dropout(0.1),
            nn.Linear(hidden_size, num_cwe_classes) # Output 15 logits
        )

    def forward(self, input_ids, attention_mask, labels=None, cwe_encoded=None, **kwargs):
        # 1. Pass through UniXCoder
        outputs = self.encoder(input_ids=input_ids, attention_mask=attention_mask)
        
        # UniXCoder equivalent of [CLS] token is the first token
        sequence_output = outputs[0] 
        cls_embedding = sequence_output[:, 0, :] 
        
        # 2. Pass through classifiers
        bin_logits = self.classifier_bin(cls_embedding).squeeze(-1) # Shape: (batch_size,)
        cwe_logits = self.classifier_cwe(cls_embedding)             # Shape: (batch_size, 15)
        
        # 3. Format output for HuggingFace Trainer
        # Trainer expects 'logits' as the primary key for evaluation
        return {
            "logits": bin_logits,
            "cwe_logits": cwe_logits
        }

print("7. Defining Custom Trainer and Metrics (Full Table Version)...")

class MultiTaskTrainer(Trainer):
    # Added **kwargs to gracefully handle unexpected arguments from Trainer
    def compute_loss(self, model, inputs, return_outputs=False, **kwargs):
        # Extract labels
        labels = inputs.pop("labels")
        cwe_labels = inputs.pop("cwe_encoded")
        
        # Forward pass
        outputs = model(**inputs)
        bin_logits = outputs["logits"]
        cwe_logits = outputs["cwe_logits"]
        
        # ---------------------------------------------------
        # LOSS 1: BINARY BCE WITH POS_WEIGHT (From EDA: 45.44)
        # ---------------------------------------------------
        pos_weight = torch.tensor([45.44]).to(bin_logits.device)
        loss_fct_bin = nn.BCEWithLogitsLoss(pos_weight=pos_weight)
        loss_bin = loss_fct_bin(bin_logits, labels.float())
        
        # ---------------------------------------------------
        # LOSS 2: CWE MULTI-CLASS WITH MASKING
        # ---------------------------------------------------
        # ignore_index=-100 ensures Clean codes don't affect this loss
        loss_fct_cwe = nn.CrossEntropyLoss(ignore_index=-100)
        loss_cwe = loss_fct_cwe(cwe_logits, cwe_labels)
        
        # ---------------------------------------------------
        # TOTAL LOSS: E1.3 Multi-task formulation (Lambda = 0.2)
        # ---------------------------------------------------
        LAMBDA = 0.2
        total_loss = loss_bin + LAMBDA * loss_cwe
        
        return (total_loss, outputs) if return_outputs else total_loss

# Evaluation Metrics matching the exact table columns
def compute_metrics(eval_pred):
    logits, labels = eval_pred.predictions[0], eval_pred.label_ids
    
    # Convert logits to probabilities using Sigmoid
    probs = 1.0 / (1.0 + np.exp(-logits)) # Sigmoid function
    
    # Use default 0.5 threshold for standard metrics calculation
    preds = (probs > 0.5).astype(int)
    
    # 1. PR-AUC (Primary Metric for Checkpointing)
    precision_curve, recall_curve, _ = precision_recall_curve(labels, probs)
    pr_auc = auc(recall_curve, precision_curve)
    
    # 2. Accuracy, MCC, Precision, Recall, F1
    accuracy = accuracy_score(labels, preds)
    mcc = matthews_corrcoef(labels, preds)
    precision = precision_score(labels, preds, zero_division=0)
    recall = recall_score(labels, preds, zero_division=0)
    f1 = f1_score(labels, preds)
    
    # 3. False Positive Rate (FPR)
    # confusion_matrix returns: [[TN, FP], [FN, TP]]
    tn, fp, fn, tp = confusion_matrix(labels, preds).ravel()
    fpr = fp / (fp + tn) if (fp + tn) > 0 else 0.0
    
    return {
        "accuracy": accuracy,
        "mcc": mcc,
        "precision": precision,
        "recall": recall,
        "f1": f1,
        "fpr": fpr,
        "pr_auc": pr_auc
    }

# CELL: TÌM NGƯỠNG TỐI ƯU & TEST NHANH TẬP PAIRED
# ==========================================
import numpy as np
from sklearn.metrics import precision_recall_curve
import torch
from tqdm import tqdm

print("1. Viết lại hàm chỉ lấy Xác suất (không chốt cứng 0.5)...")
def get_probs_only(data_loader, desc):
    all_labels = []
    all_probs = []
    with torch.no_grad():
        for batch in tqdm(data_loader, desc=desc):
            input_ids = batch[0].to(device)
            attention_mask = batch[1].to(device)
            labels = batch[2].numpy()
            
            bin_logits, _ = model(input_ids, attention_mask)
            # Chỉ lấy xác suất (probs), chưa vội chốt nhãn (preds)
            probs = torch.sigmoid(bin_logits).cpu().numpy()
            
            all_labels.extend(labels)
            all_probs.extend(probs)
    return np.array(all_labels), np.array(all_probs)

# ---------------------------------------------------------
# 2. CHẠY TRÊN TẬP VAL ĐỂ TÌM NGƯỠNG (Mất ~1 phút)

# Tạo val_loader nếu Notebook này chưa có (copy từ file Train sang)
from torch.utils.data import DataLoader, TensorDataset
val_df = pd.read_json(f"{DATA_DIR}/val_frozen.jsonl", lines=True)
val_encodings = tokenizer(val_df['func_code'].tolist(), padding="max_length", truncation=True, max_length=512, return_tensors="pt")
val_labels_tensor = torch.tensor(val_df['label'].tolist(), dtype=torch.long)
val_loader = DataLoader(TensorDataset(val_encodings['input_ids'], val_encodings['attention_mask'], val_labels_tensor), batch_size=32, shuffle=False)

val_labels, val_probs = get_probs_only(val_loader, "Evaluating Val (Finding Threshold)")

precisions, recalls, thresholds = precision_recall_curve(val_labels, val_probs)
# Tính F1-Score cho mọi ngưỡng có thể (cộng 1e-8 để tránh chia cho 0)
f1_scores = (2 * precisions * recalls) / (precisions + recalls + 1e-8)
optimal_idx = np.argmax(f1_scores)
optimal_threshold = thresholds[optimal_idx]

print(f"\n🎯 NGƯỠNG TỐI ƯU TÌM ĐƯỢC LÀ: {optimal_threshold:.4f}\n")

# ---------------------------------------------------------
vul_mask = (pair_labels == 1)
clean_mask = (pair_labels == 0)

acc_vul = (pair_preds[vul_mask] == 1).sum() / vul_mask.sum() * 100
acc_clean = (pair_preds[clean_mask] == 0).sum() / clean_mask.sum() * 100

preds_vul = pair_preds[vul_mask]
preds_clean = pair_preds[clean_mask]

if len(preds_vul) == len(preds_clean):
    paired_acc = ((preds_vul == 1) & (preds_clean == 0)).sum() / len(preds_vul) * 100
else:
    paired_acc = 0.0

print(f"--- KẾT QUẢ PAIRED SAU KHI ĐỔI NGƯỠNG ---")

print(f"Độ chính xác trên cặp (Paired Acc): {paired_acc:.2f}%\n")
